# 分层代码评审（Layered Code Review）

通用的需求 / diff / PR / 代码评审流程，做成可复用的 Cursor Skill。

目标：**机器先拦常规问题，人只盯风险与方向**；少占注意力，同时不抬高回滚与事故成本。

> **本流程只出 findings，从不代替人批准合并。**

## 何时用

给出（或指向）以下任一内容并要求评审、挑刺、合不合规、能不能合：

- 需求 / 规格 / 验收标准
- 代码片段、文件路径、diff、PR 链接
- 「按这个需求写/改的代码帮我审一下」

## 怎么用（Cursor）

1. 把本仓库克隆到本机，或把 `.cursor/skills/layered-code-review/` 拷进你的项目。
2. 在 Cursor 里用 `/` 或 `@` 唤起技能 **分层代码评审**（见该目录下的 `SKILL.md`）。
3. 粘贴需求、diff、PR 链接或代码，说「帮我审」。

也可直接把 `SKILL.md` 正文当作系统提示 / Agent 规则使用，不依赖 Cursor Skill 机制。

## 评审层（摘要）

| 层 | 看什么 |
|----|--------|
| L1 需求对齐 | 验收是否覆盖、有无范围蔓延、边界与失败态 |
| L2 正确性 | 逻辑、边界、竞态、回归面 |
| L3 安全与数据 | 注入、越权、密钥、敏感日志 |
| L4 可运维与可回滚 | 如何验证、如何关/回滚、爆轰半径 |
| L5 可维护性（克制） | 只会标让后续改动变贵的结构性问题 |

风险档由**改动**定：低（文案/默认关闭开关）→ 中（普通产品逻辑/API）→ 高（鉴权/计费/CI/迁移/不可逆）。

## 输出约定

每条发现固定为：

```
- [Important|Nit|Pre-existing] 路径或模块 · 一句话问题
  依据：文件/符号/需求条目
  为何重要：机制上一句
  建议：可执行的下一步
```

- **Important**：会坏行为、安全、数据或不可逆运维  
- **Nit**：可选改进，默认少写  
- **Pre-existing**：本次未引入，但影响合入判断时标明  

审阅结束必须写明：**本审阅 ≠ 批准合并**。同一 PR/需求连审到第 3 轮仍大量 Important 时，先重想方案或补验证，再继续细节。

## 仓库可选配套

项目里若已有 `CLAUDE.md` / `AGENTS.md` / `.cursor/rules` / `REVIEW.md`，评审时应一并读入。没有也不强求；需要时可参考 [`templates/REVIEW.md`](templates/REVIEW.md) 补一份短模板（失败定义 + 敏感路径）。

## 设计来源

流程借鉴「分层拦问题、风险档决定人审深度、不把 bot 审批当人类审批」的工程实践（参见 [Solving code review at Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/)）。本仓库是独立的可复用模板，不隶属任何厂商。
