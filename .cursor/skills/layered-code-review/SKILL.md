# 分层代码评审

通用审阅流程，借鉴「机器先拦常规问题、人只盯风险与方向」：目标是少占人的注意力，同时不抬高回滚/事故成本。**本 skill 只出 findings，从不代替人批准合并。**

## 何时用

用户给出（或指向）以下任一内容并要求评审、挑刺、合不合规、能不能合：
- 需求 / 规格 / 验收标准
- 代码片段、文件路径、diff、PR 链接
- 「按这个需求写/改的代码帮我审一下」

缺材料时先问最少必要项：要审什么、相对哪份需求、风险敏感点（钱/鉴权/数据/发布）。能从仓库或对话里拿到的，自己取，不问已知。

## 输入整理（先做）

1. **意图**：用一句话写清「这次改动要解决什么 / 不解决什么」。
2. **范围**：改了哪些路径；哪些是生成代码、哪些是手写约束。
3. **证据**：有没有可跑的验证（测试命令、构建、截图、复现步骤）。没有就标「未验证」，不要假装跑过。
4. **风险档**（由改动定，不由作者定）：
   - **低**：文案/文档、纯加性且默认关闭的开关、无用户面行为变化
   - **中**：普通产品逻辑、缓存、对外 API 形状、系统提示词类配置
   - **高**：鉴权/计费/支付、自动更新、CI/发布工作流、数据迁移、密钥与权限、不可逆操作

## 评审层（按序，能跳过已覆盖的）

对每一层只报**真问题**；风格偏好、纯口味 nit 默认丢掉，除非用户明确要风格审。

### L1 · 需求对齐
- 实现是否覆盖验收标准；有没有多做的范围蔓延。
- 边界与失败态是否写清（空输入、权限不足、并发、超时）。

### L2 · 正确性
- 逻辑错误、边界、竞态、资源泄漏、错误吞掉。
- 新代码是否破坏既有不变量；回归面在哪。

### L3 · 安全与数据
- 注入、越权、密钥进仓/进日志、不安全反序列化、路径穿越、SSRF 类风险。
- 用户数据最小化与敏感日志。

### L4 · 可运维与可回滚
- 如何验证（测什么）；如何一键关/回滚；爆轰半径（谁受影响）。
- 缺 feature flag / 迁移回滚方案时，高风险档必须点名。

### L5 · 可维护性（克制）
- 只标会让后续改动变贵的结构性问题（错误抽象、隐式全局状态、无测试的核心路径）。
- 不刷命名洁癖；同类问题归一类，要求修全类而非改一行。

## 输出格式（固定）

先给 **总判**（2–4 句）：风险档、能不能在现有检查下前进、最大缺口。

再列 **发现**，每条必须：

```
- [Important|Nit|Pre-existing] 路径或模块 · 一句话问题
  依据：文件/符号/需求条目（能定位就定位；猜的要标明「推测」）
  为何重要：机制上一句
  建议：可执行的下一步（修法或验证命令），不写空话
```

- **Important**：会坏行为、安全、数据或不可逆运维
- **Nit**：可选改进；默认少写
- **Pre-existing**：本次 diff 没引入，但会影响合入判断时标明

无问题时写：`发现 0。剩余风险：…（机器层仍可能漏什么）`

最后给 **人仍须拍板的点**（方向/高风险路径/架构范式/是否接受未验证项），并明确：**本审阅≠批准合并**。

## 收敛规则（防无限互刷）

- 同一轮：同类 bug 合并成一类，指出模式。
- 用户修完再审：优先只审**新 diff**；已关闭且理由成立的点不重复刷。
- 同一 PR/需求连续审到第 **3** 轮仍大量 Important：停改细节，要求用户先重想方案或补验证，再继续。
- Agent 生成的「已修好」声明不算证据；要看 diff 或测试输出。

## 仓库内可选配套（有则读，无则跳过）

若仓库存在则加载进上下文，并检查本次改动是否违反或过时：
- `CLAUDE.md` / `AGENTS.md` / `.cursor/rules`：栈、约定、非目标
- `REVIEW.md`：该区域失败长什么样、要跳过的路径、证据要求

没有这些文件时，用本 skill 默认层即可；需要时可建议用户补一份短 `REVIEW.md`（失败定义 + 敏感路径），不要强行创建除非用户要求。

## 禁止

- 用类比或「最佳实践」空话代替对这份 diff/需求的机制判断
- 把愿望当结论（「应该没问题」）
- 代替人做合并批准，或把 bot 审批算作人类审批
- 伪造测试结果、覆盖率、CI 状态
